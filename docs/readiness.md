# Сверка с ТЗ и путь до реального сервиса

Источник обязательных требований — PDF HackAlem AI, русский раздел, страницы 2–5. Исходный пользовательский промпт дополнительно задаёт стек, формулу и способы проверки. Заявки добавлены по отдельному запросу пользователя; они не подменяют обязательный сценарий рекомендации.

| Пункт | Что сделано | Что ещё подтверждать |
|---|---|---|
| Вход: город, дата, формат, категория, бюджет; язык/часы опционально | Форма, Pydantic, строгие проверки | Пройти сценарий на машине презентации |
| Каталог выбранного города, до трёх кандидатов | Фильтры, рейтинг, стабильная сортировка | Нет скрытого расширения города |
| Занятость, ограничения, площадки | Единый пайплайн для всех категорий | Доступность только по календарю датасета |
| Конкретные объяснения, 1–2 предложения | Семантический E5-подбор, проверенные факты и цитаты | Человеческая оценка различий; живой LLM после ключа |
| Повторяемость и две разные даты | Кеш первого принятого текста, проверенная пара 04/05 октября | Финальная репетиция команды |

## Что происходит после выбора

1. Клиент выбирает профиль и проверяет подготовленные условия.
2. При настроенном канале указывает контакт и разрешает передачу команде. Без канала доступен только файл условий — персональные данные не собираются.
3. Сервер заново проверяет профиль и условия, сохраняет обращение и пытается передать команде.
4. Пользователь видит фактический статус: принято каналом передачи, ошибка доставки или неизвестный результат. Для SMTP принятие сервером не подтверждает получение/прочтение письма; это не согласие подрядчика и не бронь.
5. Сотрудник связывается с клиентом, находит настоящего исполнителя и согласует доступность, цену и договор отдельно.

Синтетические профили никогда не принимают реальных заявок. Даже остальные имена анонимизированы: ID и описание не позволяют приложению самостоятельно позвонить исполнителю. Изобретать контакты или подтверждать заказ на основании `busy_dates` нельзя.

## Данные, которые нужны от команды

- Настроить SMTP согласованного email-канала и проверить доставку. Секреты — только в локальном `.env` / защищённом окружении сервера.
- Новый ключ LLM вместо ключей, опубликованных в переписке, доступ к выбранной модели и оплаченный API-баланс при необходимости.
- Для настоящего каталога: разрешённые контакты исполнителей и актуальные календарь/цены.
- Для публичной ссылки: выбранный хостинг и доступ к нему. `127.0.0.1` открывает сайт только на компьютере, где запущен сервер.

## Сдача и Git

Официальный PDF не задаёт название ветки, обязательный merge или публичный URL. Пользователь выбрал `demoVer-1` для всей разработки. Перед сдачей проверяются тесты, README, запуск и демонстрационный сценарий.

На момент последней проверки `main` был заменён отдельным корневым коммитом и не имел общего предка с `demoVer-1`. Нельзя делать force push поверх чужого состояния. Если истории остаются несвязанными, создать интеграционную ветку от свежего `main`, выполнить merge `demoVer-1` с `--allow-unrelated-histories`, разрешить README в пользу документации продукта и открыть PR в `main`. После ревью и CI выполнить обычный merge. Перед этим заново проверить ветки: состояние GitHub могло измениться.

GitHub Actions ранее завершался до запуска шагов, без доступных логов. Причина не установлена; локальные тесты не заменяют успешный контейнерный прогон. Не объявлять CI зелёным без фактического результата.
